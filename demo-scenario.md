# Демонстрационные сценарии

Копируемые команды для 5 обязательных сценариев. Запускаем CLI один раз:

```bash
./gradlew clean jar
java -jar build/libs/raft.jar
```

Все команды ниже вводятся вручную в приглашении `raft>`, по одной. Между командами, меняющими состав
кластера (`startCluster`, `killNode`, `startNode`, `partition`, `healPartition`), дайте кластеру
секунду-две устаканиться, прежде чем проверять состояние через `leader`/`status` — выборы и репликация
асинхронны. Логи узлов — в `data/<id>.log`; запустите `tail -f data/n*.log` в другом терминале, чтобы
видеть выборы, репликацию и попадание журнала на диск в реальном времени.

---

## Сценарий 1 — Нормальная работа

```text
startCluster --clean
leader                 # ровно один лидер, в одном term'е
put x 1
put y 2
get x                  # => 1
status                 # все 5 узлов: одинаковый commitIndex (=2) и logLength (=2)
logDump --node n1
logDump --node n3      # идентичен n1
```

Ожидается: один лидер в term 1; `get x` возвращает `1`; после репликации каждый узел показывает
`commitIndex=2, logLength=2`; два `logDump`'а совпадают entry-за-entry.

## Сценарий 2 — Падение лидера и восстановление

```text
startCluster --clean
put x 1
put y 2
leader                 # запомните лидера, например n1
killNode n1            # System.exit; состояние n1 остаётся на диске
leader                 # НОВЫЙ лидер в БОЛЬШЕМ term'е (например, n3, term 2)
put z 9                # коммитится через нового лидера
status                 # n1 = DOWN; остальные 4 на commitIndex=3
startNode n1           # заново порождаем n1 с тем же data dir → восстановление из журнала
status                 # n1 вернулся, тот же commitIndex=3, что у всех
logDump --node n1      # пропущенный "put z 9" (новый term) теперь на месте
```

Ожидается: 4 выживших выбирают нового лидера в большем term'е; `put z 9` коммитится; перезапущенный
`n1` догоняет через AppendEntries, и его log/commitIndex совпадают с кластером.

## Сценарий 3 — Split vote / разделение кворума

```text
startCluster --clean
put a 1
leader                              # например, n1 в term 1
partition n1,n2 n3,n4,n5           # режем кластер надвое
leader                              # меньшинство n1/n2 держит устаревшего лидера; большинство выбирает лидера в большем term'е
status                             # commitIndex меньшинства ЗАМОРОЖЕН; большинство продвигается
putTo n1 b 2                       # запись прямо в лидера меньшинства → нет кворума
                                   #   => ERROR (он дописывает, но не может закоммитить: 2 < 3)
put b 2                            # CLI направляет запрос лидеру большинства (больший term) → OK
status                             # commitIndex большинства продвинулся; меньшинство всё ещё заморожено
healPartition
status                             # кластер сходится: меньшинство принимает больший term, журналы выравниваются
leader
```

Ожидается: меньшинство `{n1,n2}` не может собрать большинство (2 < 3) — его кандидаты бесконечно
инкрементируют term без победы, а запись, нацеленная в него, никогда не коммитится. Большинство
`{n3,n4,n5}` выбирает лидера и обслуживает `put`. После `healPartition` отставшая сторона принимает
больший term, и журналы снова сходятся (единый `status`).

## Сценарий 4 — Расходящийся журнал (усечение никогда-не-закоммиченных записей)

```text
startCluster --clean
put x 1
leader                  # например, n1
setDelay n1 8000        # задержка peer-RPC у n1 в ОБЕ стороны → он не реплицирует/не шлёт heartbeat
                        #   И не слышит больший term, поэтому остаётся «застрявшим» лидером term 1 (окно)
putTo n1 y 2            # n1 дописывает "y@2" локально (term 1); до большинства она не доходит
                        #   подождите ~2-3 с: голодающие follower'ы выбирают нового лидера в term 2
logDump --node n1       # n1 всё ещё показывает расходящийся, НЕЗАКОММИЧЕННЫЙ [x@1, y@2(term1)]
leader                  # новый лидер большинства, term 2
killNode n1             # убиваем n1 внутри окна задержки (незакоммиченный y остаётся на его диске)
put z 9                 # новый лидер коммитит z на index 2 (term 2)
logDump --node n2       # журнал большинства: [x@1, z@2(term2)]   (без "y")
startNode n1            # n1 переподключается …
logDump --node n1       # … новый лидер делает backtrack до общего префикса, УСЕКАЕТ "y",
                        #    и n1 теперь совпадает: [x@1, z@2(term2)]
status                  # все согласованы
```

Ожидается: до kill'а `logDump n1` показывает расходящийся незакоммиченный `y`; у большинства его не
было. После переподключения `n1` лидер откатывает `sentLength` до общего префикса, follower усекает
свой конфликтующий хвост и дозаписывает записи лидера. **Усечённый `y` никогда не был committed** —
Leader Completeness гарантирует, что закоммиченные записи не теряются, отбрасываются только
незакоммиченные расходящиеся хвосты.

(Чтобы увидеть именно многораундовый **backtrack**: изолируйте один узел через
`partition n5 n1,n2,n3,n4`, сделайте несколько `put`'ов, затем `healPartition` — первый AppendEntries
лидера промахивается, и `sentLength[n5]` шагает вниз раунд за раундом, пока префиксы не совпадут, после
чего n5 догоняет.)
